    Detailed report
    
  
    A user's search results come from a warm cache. An admin revokes their access. The next search and the old document link should both reflect that, without clearing the cache.

    Request path
    
  
    The permission check sits between candidate retrieval and text loading. The cache only covers the first step.
    
  
    
    
    CandidatesThe cache, or FTS5 on a miss, returns ranked document IDs for the query. Nothing user-specific.
    
    
    Current ACLA join on doc_grants and memberships keeps only IDs the user can read now.
    
    
    Load textTitles and bodies are read only for permitted IDs.
    
    
    SnippetsSnippets are built only from permitted text, then the response is sent.
    
  
    
  
      
    
    • {{REF_SEARCH}}: the whole path in one function.
      • 
    
    • {{REF_CACHE}} and {{REF_FTS}}: candidate IDs. FTS5 terms are quoted, so user input can't use FTS operators.
      • 
    
    • {{REF_ACL}}: the ACL filter, which keeps ranking order.
      • 
    
    • {{REF_LOAD}} and {{REF_SNIPPET}}: text and snippets for permitted IDs only. {{REF_T_LOAD}} records the SQL and checks that the restricted ID never reaches the text query.
      • 
    
    • {{REF_GETDOC}}: direct links use the same ACL join and return the same 404 for "forbidden" and "doesn't exist".
      • 
  
    

  
    Transaction boundary
    
  
    The ACL filter and the text load run inside one SQLite read transaction. The database is in WAL mode, so that transaction reads from one snapshot, fixed at its first read. Revocation is a separate write transaction ({{REF_REVOKE}}, BEGIN IMMEDIATE). There are only two cases:
    
  
      
    
    • The revocation committed before the search's snapshot. The ACL filter drops the document, so its text is never read.
      • 
    
    • The revocation committed after the snapshot. That one search is consistent with the old permissions, both for the ACL and the text. The next search enforces the revocation.
      • 
  
    
  
    {{REF_T_TX}} covers both cases. It commits a revocation from a second connection between the ACL filter and the text load. The in-flight search returns its consistent snapshot, and the next search (still a cache hit) drops the Finance document.
    
  
    Why warm candidate IDs are safe to reuse. A cache entry is a list of document IDs that match the query text. It doesn't hold titles, text, or permission decisions. A permission change doesn't change which documents match the words, so the cached list stays correct. What changes is which of those IDs survive the ACL filter, and that runs on every request. The cache never needs to be cleared when access changes, and one user's entry can serve another user.

    Scope
    
  
    
    
    Covered
      
      
    • Every search and direct-link request that starts after the revocation commits.
      • 
      
    • Requests from any user, whether the cache was warmed by them or by someone else.
      • 
    
    
    
    Not covered
      
      
    • Copies already delivered: a page left open, a downloaded file, a response already rendered on screen.
      • 
      
    • Offline devices or clients with local copies. Revoking server access doesn't erase data already on a device.
      • 
      
    • A search whose snapshot was taken before the commit. It finishes with the old permissions.
      •

    Why I built this
    
  
    
    
    Working on retrieval tools made me curious about what happens when the index knows about a document but the person searching can no longer open it.
    
    
    I wanted to test that with a warm cache, because the system already knows which documents match.
    
    
    Access Revoked shows where the permission check has to happen so that the next search and the old document link both honor the change.
